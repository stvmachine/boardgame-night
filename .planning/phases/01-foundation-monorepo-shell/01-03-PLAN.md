Build the deployment vertical slice: a single Docker image that contains both the Rails 8.1.3 API and the compiled Vue 3.5.35 SPA, plus a Kamal 2 `config/deploy.yml` scaffold with scaffold server/registry/secrets. <threat_model>
## Trust Boundaries

| Boundary | Description |
|------------|-------------|
| Local filesystem → Docker build context | `.dockerignore` filters what crosses into the image build; the `.env.bggeek.keys` / `.env.keys` private key boundary is the hazmat layer |
| Build stage → Runtime stage | The Node build stage may carry extra files; `COPY --from=build /app /app` transfers the compiled SPA and Rails app into the final stage |
| Image → Deploy runtime (Phase 2+) | `DOTENV_PRIVATE_KEY_BGGEEK` and `RAILS_MASTER_KEY` cross this boundary via Kamal `env.secret` at deploy time, not at build time |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-01 | Credential Theft | `.env.bggeek.keys` / `.env.keys` baked into a Docker image layer | high | mitigate | `.dockerignore` excludes both key files; the `docker_verify` task asserts `! test -e /app/.env.bggeek.keys && ! test -e /app/.env.keys` against the final image; multi-stage build ensures the Node stage's `COPY . .` is filtered by `.dockerignore` before files enter any stage |
| T-3-02 | Tampering | `DOTENV_PRIVATE_KEY_BGGEEK` baked as ARG/ENV in Dockerfile | high | mitigate | Dockerfile has no `ARG`/`ENV` referencing `DOTENV_PRIVATE_KEY_BGGEEK`; the secret flows only via Kamal `config/deploy.yml` `env.secret` at runtime (D-14) |
| T-3-03 | Information Disclosure | Single image containing both Rails and SPA | medium | accept | PITFALLS #10 deliberately chooses one container over two — same origin in production, no CORS, atomic deploy; the tradeoff is per-design and later phases mitigate by isolating the SPA's runtime blast radius from the /graphql schema surface |
| T-3-04 | Denial of Service | Vite build broken in Dockerized Node stage | low | mitigate | Plan 03 Task 1 inspects the Rails-8-generated Dockerfile first and patches or replaces the build stage to run `bin/vite build`; the `docker_verify` task fails fast if `public/index.html` is missing |
| T-3-05 | Spoofing | Accidental `kamal deploy` or `docker push` to scaffold registry | low | mitigate | Plan 03 contains no `kamal deploy` or `docker push` invocation in any action or verification; the prohibition is enforced in must_haves and task instructions |
| T-3-SC | Tampering | kamal gem and dotenvx npm install inside the Docker image | high | mitigate | `kamal` 2.12.0 is the Rails 8 default; `@dotenvx/dotenvx` is the official package from the dotenvx organization (verified in RESEARCH.md Sources); slopcheck passed at research time; no human-verify checkpoint needed |
</threat_model>
