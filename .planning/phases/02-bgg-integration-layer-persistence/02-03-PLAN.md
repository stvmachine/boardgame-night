    ```ruby
    # frozen_string_literal: true

    # Bgg::CollectionFetcher handles the two-call expansion workaround for BGG
    # collection fetches. BGG has a known bug where boardgame expansions are
    # returned with the wrong subtype when using subtype=boardgame. To work
    # around this, we make two calls:
    #   1. excludesubtype=boardgameexpansion → base games only (correct subtype)
    #   2. subtype=boardgameexpansion → expansions only (correct subtype)
    #
    # Results are merged into a single normalized collection hash.
    # Falls back to a single subtype=boardgame call if the workaround fails.
    #
    # Ported from bgg-graphql-proxy/src/datasources/bggDataSource.ts:
    # getUserCollectionWithExpansionWorkaround() + getUserCollectionFallback()

    class Bgg::CollectionFetcher
      def initialize(client: nil, normalizer: nil)
        @client = client || Bgg::Client.new
        @normalizer = normalizer || Bgg::Normalizer.new
      end

      # Fetches a user's full collection (base games + expansions merged).
      #
      # Returns a normalized collection hash from Bgg::Normalizer:
      #   { total_items: Integer, pub_date: String, items: Array }
      #
      # Raises Bgg::CollectionNotReadyError if BGG returns 202 after 5 retries.
      # Raises Bgg::InvalidUsernameError if the user doesn't exist.
      # Raises Bgg::NetworkError on transport failures.
      def fetch(username)
        merged_doc = fetch_with_workaround(username)
        @normalizer.normalize_collection(merged_doc)
      rescue Bgg::ClientError, Bgg::ServerError, Bgg::NetworkError => e
        Rails.logger.warn("[Bgg::CollectionFetcher] Workaround failed for '#{username}': #{e.message}. Falling back to single call.")
        fallback(username)
      end

      private

      # D-09: Two-call expansion workaround
      def fetch_with_workaround(username)
        # Call 1: Base games (excluding expansions)
        boardgames_doc = @client.request_with_202_retry(:collection,
          username: username,
          excludesubtype: "boardgameexpansion",
          own: 1,
          stats: 1
        )

        # Call 2: Expansions only
        expansions_doc = @client.request_with_202_retry(:collection,
          username: username,
          subtype: "boardgameexpansion",
          own: 1,
          stats: 1
        )

        merge_docs(boardgames_doc, expansions_doc)
      end

      # D-10: Fallback — single call with no subtype filter
      def fallback(username)
        doc = @client.request_with_202_retry(:collection,
          username: username,
          own: 1,
          stats: 1
        )
        @normalizer.normalize_collection(doc)
      end

      # Merges two Nokogiri documents into one combined document.
      # Takes all <item> elements from both docs and creates a new <items> root.
      def merge_docs(doc_a, doc_b)
        boardgame_items = doc_a.css("item")
        expansion_items = doc_b.css("item")

        total_count = boardgame_items.length + expansion_items.length

        merged = Nokogiri::XML::Document.new
        root = merged.create_element("items")
        root["totalitems"] = total_count.to_s
        root["pubdate"] = doc_a.at_css("items")&.attr("pubdate") ||
                          doc_b.at_css("items")&.attr("pubdate") || ""

        all_items = boardgame_items + expansion_items
        all_items.each { |item| root.add_child(item.dup) }
        merged.root = root
        merged
      end
    end
    ```

    Key design notes:
    - **D-09 per RESEARCH.md**: Two calls means 2 rate-limited requests. Each call waits for the 5s throttle gap independently. This is expected behavior — in practice the collection fetch takes ~10s minimum (2 × 5s rate limit gaps).
    - **D-10**: The fallback catches `Bgg::ClientError`, `Bgg::ServerError`, and `Bgg::NetworkError`. Notably, `Bgg::CollectionNotReadyError` (from 202 exhaustion) IS a `Bgg::ClientError` subclass, so the fallback also catches the "BGG is still preparing data after 5 retries" case.
    - **Merging strategy**: Raw Nokogiri documents are merged at the XML level (not at the hash level) to keep the normalizer as the single hash-creation path. Both docs' `<item>` elements are collected into a new `<items>` root document.
    - **`request_with_202_retry`**: The CollectionFetcher calls `Bgg::Client#request_with_202_retry` (defined in Plan 01) which wraps the rate limiter + 202 retry loop. Each call is independently throttled and retried.

    **D-11, D-12, D-13:** Create `app/jobs/bgg/import_collection_job.rb`:

    ```ruby
    # frozen_string_literal: true

    class Bgg::ImportCollectionJob < ApplicationJob
      queue_as :bgg_imports

      # D-11: Global concurrency 1 for all BGG jobs across all users.
      # Prevents hammering the BGG API when multiple users trigger imports.
      # The 5-minute duration ensures lock expiry if a worker crashes mid-job.
      limits_concurrency to: 1, key: "bgg_api", duration: 5.minutes

      # D-12: Transient failures — retry with polynomial backoff
      # Faraday::TimeoutError covers both open_timeout and read_timeout
      retry_on Faraday::TimeoutError, wait: :polynomially_longer, attempts: 5
      # Faraday::ServerError covers 5xx responses (BGG maintenance, overload)
      retry_on Faraday::ServerError, wait: :polynomially_longer, attempts: 5
      # Bgg::CollectionNotReadyError: BGG kept returning 202 after 5 retries
      retry_on Bgg::CollectionNotReadyError, wait: 30.seconds, attempts: 3

      # D-12: Permanent failures — discard immediately (no retry)
      # Faraday::ResourceNotFound = BGG returned 404 (invalid endpoint)
      discard_on Faraday::ResourceNotFound
      # InvalidUsernameError = BGG confirmed user doesn't exist
      discard_on Bgg::InvalidUsernameError
      # Deserialization error = job payload corrupted
      discard_on ActiveJob::DeserializationError

      # D-13: Main entry point — enqueued via perform_later(username)
      #
      # Flow:
      #   1. Validate username against BGG API (user lookup)
      #   2. Fetch collection (two-call expansion workaround)
      #   3. Persist to database
      #
      # All steps happen inside the concurrency lock. The rate limiter
      # inside Bgg::Client prevents exceeding BGG's 1-req/5s limit.
      def perform(username)
        # Step 1: Validate user exists on BGG
        validate_user!(username)

        # Step 2: Fetch collection (two-call workaround with fallback)
        collection = Bgg::CollectionFetcher.new.fetch(username)

        # Step 3: Persist to database
        Bgg::CollectionPersister.new(username, collection).persist!

        Rails.logger.info("[Bgg::ImportCollectionJob] Successfully imported collection for '#{username}' " \
                          "(#{collection[:total_items]} items)")
      end

      private

      def validate_user!(username)
        client = Bgg::Client.new
        user_doc = client.user(username)

        # BGG returns <user id="..." name="..."> for valid usernames
        # Invalid usernames return an empty response or error
        user_node = user_doc.at_css("user")
        if user_node.nil? || user_node.attr("id").to_s.empty?
          raise Bgg::InvalidUsernameError,
            "BGG user '#{username}' not found or invalid"
        end

        Rails.logger.debug("[Bgg::ImportCollectionJob] Validated user '#{username}' (BGG ID: #{user_node.attr('id')})")
      end
    end
    ```

    Key design notes:
    - **D-11**: `limits_concurrency to: 1, key: "bgg_api"` — Solid Queue uses this key to ensure at most 1 BGG job runs globally. The `duration: 5.minutes` handles lock expiry if a worker crashes. Per RESEARCH.md Pitfall 2, this is the primary defense against simultaneous BGG requests.
    - **D-12**: `retry_on` ordering matters — more specific errors first. `Faraday::ServerError` is a subclass of `Faraday::Error` so it must come before any catch-all. Similarly, `Faraday::TimeoutError` and `Faraday::ServerError` are siblings (both extend `Faraday::Error`).
    - **D-12**: `discard_on` for permanent failures means the job is silently removed from the queue and never retried. The frontend will need to check last-import status to surface errors — this is a Phase 3 concern.
    - **D-13**: The `perform` method takes a single `username` argument (String). Enqueue via `Bgg::ImportCollectionJob.perform_later("stevmachine")`.
    - **User validation**: `client.user(username)` is a separate rate-limited BGG call that happens BEFORE the collection fetch. This adds ~5s to the start of each import but prevents wasting API calls on invalid usernames.
    - **Solid Queue retry interaction with faraday-retry (RESEARCH.md Pitfall 5)**: faraday-retry (max 3 attempts) handles intra-request blips. ActiveJob `retry_on` (max 5 attempts) handles inter-request resilience. Total potential attempts per BGG call = 3 (faraday-retry) × 5 (ActiveJob retries) = 15. This is acceptable for BGG's flaky infrastructure.
