# Phase 12: Dev Blog Engine - Context

**Gathered:** 2026-08-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Publish a small engineering blog sourced from `docs/development/*.md`, generated by a pure-Ruby static-site builder into the existing Rails/Kamal image, available through a same-origin `/blog` fallback and a configurable blog subdomain. The phase includes the accepted engine contract, safe parsing/rendering, current architecture content, deployment integration, CI, maintainer docs, and real deployment verification. It does not add a general documentation platform.

</domain>

<decisions>
## Implementation Decisions

### Engine contract and carried-plan reconciliation
- **D-01:** Preserve ADR-014 as the accepted engine decision: custom plain-Ruby classes using Psych safe loading, kramdown, and ERB. Plan 12-01 must revalidate and update the existing ADR instead of recreating it or repeating already-complete comparison research. — **Reversibility:** costly — changing engines after templates, tests, and the published URL contract exist would replace most Phase 12 implementation.
- **D-02:** Replan all six carried plans before execution. They were authored before Phase 13 and contain stale assumptions: Vue is no longer the active frontend, ADR-014 already exists, the auth post contains Vue/Pinia snippets, and proposed 2026-07-21 filenames no longer represent new work.
- **D-03:** Add `kramdown` as the only required blog gem unless implementation proves another dependency essential. Rouge/syntax highlighting is deferred unless the actual post corpus requires it.

### Content currency and editorial contract
- **D-04:** Blog content must describe the shipped React 19 + Apollo Client application and current Rails code. Vue-era decisions may appear only as explicitly labeled history or superseded context.
- **D-05:** Update the existing authentication post in place so its frontend examples match `AuthContext`/React and the current token persistence behavior. New posts use their real creation date and cite actual current files plus relevant ADRs.
- **D-06:** Keep the four planned architecture topics—merged collection, board-game-night lifecycle, GraphQL wiring, and challenges/decisions—but revise outlines against current code and Phase 13 outcomes. At least one code excerpt and one ADR link remain required per post.
- **D-07:** Generated content is trusted repository-authored markdown, but YAML still uses `Psych.safe_load`; raw HTML and script injection are not enabled by default. Templates must escape metadata and only inject converter-produced body HTML through an explicit boundary.

### Build isolation and deterministic output
- **D-08:** Keep the builder as plain Ruby that can run without booting Rails or decrypting `.env.bggeek`. Provide `bin/build-dev-blog` as the canonical CLI and a Rake wrapper for maintainers. — **Reversibility:** costly — Rails-boot coupling would make Docker/CI builds depend on runtime secrets and initializers.
- **D-09:** Output remains `public/dev-blog/`; builds are idempotent, remove stale generated files, exclude drafts by default, sort by date descending, and produce deterministic index/post paths.
- **D-10:** Do not commit generated `public/dev-blog/` output unless existing repository policy requires it; source markdown, templates, builder, and tests are canonical. Docker and CI regenerate the site.

### Deployment and routing
- **D-11:** Support both `/blog` on the primary host and a configurable host constraint (`DEV_BLOG_HOST` or one consistently named equivalent). Do not hardcode `app.example.com`, `youruser`, the placeholder VPS address, or an unconfigured production domain. — **Reversibility:** costly — the chosen host env name and public URL shape become deployment/maintainer contracts.
- **D-12:** Insert blog routes before the SPA catch-all. Resolve only allowlisted generated index/post paths under `public/dev-blog`; reject traversal, encoded traversal, unknown files, and hostile host values.
- **D-13:** Build the blog in the Ruby image stage after application code and production gems are available. The blog adds no container, Redis service, Node pipeline, or credential-dependent initializer bypass.
- **D-14:** Update Kamal configuration and maintainer docs with an example configurable host/proxy/DNS setup, but preserve existing deployment placeholders until real infrastructure values are supplied.

### Presentation scope
- **D-15:** Use semantic static HTML and a standalone stylesheet with readable responsive typography, visible focus states, accessible landmarks, code blocks, and `prefers-color-scheme` light/dark support. Do not load the React SPA, Tailwind runtime, or a second frontend framework.
- **D-16:** Phase 12 ships an index and post pages only. Search, comments, pagination, tag archive pages, RSS, analytics, and a CMS are outside this phase.

### Verification and release
- **D-17:** CI must build the blog and run focused parser/builder/content/routing/secret-leak tests as part of the existing Ruby workflow; it must not need BGG secrets or a browser suite.
- **D-18:** Automated verification must cover valid HTML structure, all source posts linked, stale-output cleanup, draft exclusion, metadata/body escaping, no credential strings/values, safe path handling, `/blog`, configurable-host routing, and Docker-image output.
- **D-19:** Real subdomain DNS/TLS/proxy reachability remains a blocking human-action checkpoint in the final plan. Automated `/blog` and host-constraint tests cannot substitute for a deployed request; do not claim external reachability without evidence.

### the agent's Discretion
- Exact typography values, CSS class names, template partial organization, and the consistent environment variable name for the blog host.
- Exact post prose and code excerpts, provided every claim is checked against current source and the locked topics/voice are preserved.
- Whether the Rake task delegates directly to the CLI or both call a shared Builder API.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `docs/adr/014-dev-blog-engine.md`: engine comparison and accepted decision already exist; Plan 12-01 should become reconciliation/refresh work.
- `docs/development/2026-07-21-authentication-with-rails-built-ins.md`: valid frontmatter and narrative pattern, but Vue/Pinia snippets are stale after Phase 13.
- Existing RSpec and CI Ruby setup: parser/builder/content tests can run in the current `test` job with Bundler caching.

### Established Patterns
- Rails is API-only and serves a compiled React SPA from `public/`; blog routes must precede the HTML catch-all.
- Docker currently builds React assets in a Node stage and installs production Ruby gems in the final Ruby stage; plain-Ruby blog generation fits after `COPY --from=build` without Rails boot.
- Deployment configuration intentionally contains placeholder image/host/VPS values, so Phase 12 must expose configuration rather than invent production infrastructure.
- Security-sensitive values are runtime environment secrets; generated HTML must be deterministic and secret-free.

### Integration Points
- `Gemfile`/`Gemfile.lock`: add kramdown.
- `lib/dev_blog/`, `bin/build-dev-blog`, and `lib/tasks/dev_blog.rake`: engine and entrypoints.
- `public/dev-blog/`: generated image output only.
- `config/routes.rb` and a narrow blog-serving controller: host/path routing before SPA fallback.
- `Dockerfile`: image-build generation step in the Ruby stage.
- `.github/workflows/ci.yml`: build and focused RSpec gate.
- `config/deploy.yml` and `docs/development/README.md`: configurable host/DNS/proxy operational contract.

</code_context>

<specifics>
## Specific Ideas

- Keep the blog intentionally small and editorial: one index, stable `/posts/<slug>/` pages, readable code excerpts, and no app-like client runtime.
- Treat stale Vue references as content correctness failures, not harmless historical wording, unless the surrounding text explicitly explains the migration chronology.
- The final deployment checkpoint should record the tested URL and HTTP result without writing secrets or infrastructure credentials into planning artifacts.

</specifics>
