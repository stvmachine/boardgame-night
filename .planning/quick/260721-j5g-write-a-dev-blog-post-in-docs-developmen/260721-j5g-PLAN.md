STRUCTURE (follow this outline; all facts are verifiable in the codebase — do not invent claims):

1. The problem. API-only Rails 8 backend + Vue 3 SPA, single `/graphql` endpoint. In dev the SPA
   runs on localhost:5173 and Rails on localhost:3000 (cross-origin); in production the SPA is
   served same-origin from `public/`. Auth must work in both without brittle cookie/CORS config.

2. The decision (ADR-008). Rails 8 built-in authentication adapted for API-only Bearer tokens:
   - `has_secure_password` + bcrypt on User (snippet: app/models/user.rb line 4 — copy verbatim,
     include the model's validations/associations only if they fit naturally).
   - `Session` model with `has_secure_token :token`, `expires_at`, and the `active` scope
     (snippet: app/models/session.rb, whole file is 12 lines — copy verbatim).
   - `Current < ActiveSupport::CurrentAttributes` holding session + user (app/models/current.rb).
   - `Authentication` concern resolving `Authorization: Bearer <token>` into `Current.session` /
     `Current.user` via `Session.active.find_by(token:)` (snippet: app/models/concerns/authentication.rb,
     the `authenticate` method — copy verbatim).
   - `GraphqlController` injects `current_user` / `current_session` into the GraphQL context for
     both single-query and Apollo multiplex batch modes.

3. Why not the alternatives (from ADR-008 "Alternatives Considered", expand honestly):
   - Devise: full-stack auth engine that fights API-only + SPA (controllers/views/flash you'd
     disable); over-engineered for friend-group accounts.
   - JWT access + refresh: algorithm-confusion risk, refresh rotation, and stateful revocation
     with no matching benefit at this scale; a DB session row gives revocation by `destroy`.
   - Cookie sessions: cross-origin dev pain (`credentials: 'include'` edge cases in Apollo) and
     no per-device revocation.
   Note the trade-off we accepted: one indexed `Session` lookup per authenticated request —
   negligible at v1 scale.

4. The GraphQL flow:
   - `signUp` / `signIn` mutations validate input via dry-validation contracts (SignUpContract /
     SignInContract), then create a session with `expires_at: 30.days.from_now` and return
     `{ token, user }` (snippet: app/graphql/mutations/sign_in.rb resolve body — copy verbatim;
     mention sign_up.rb follows the same shape).
   - Frontend: Apollo `setContext` link reads the token from the Pinia auth store and sends
     `Authorization: Bearer <token>` on every request (snippet: app/frontend/apollo/client.ts
     lines 22–30, the authLink — copy verbatim). Token lives in the store, NOT localStorage
     (per ADR-008).
   - `signOut` destroys the Session row — token is invalid immediately (snippet:
     app/graphql/mutations/sign_out.rb, whole file — copy verbatim). This is the revocation story
     JWT can't give you cheaply.

5. Bonus: guests without accounts. Provisional user accounts + group invite tokens (ADR-009/010)
   let invitees RSVP via a magic link without registering, then optionally upgrade to a full
   account (`upgrade_to_account` mutation) without losing RSVP history. One or two paragraphs —
   reference the ADRs, don't re-explain them in full.

6. Deliberately deferred. Password-reset flow polish, token rotation, session expiry tuning
   (30 days is a first guess), and "sign out everywhere" UI are not built yet. State this plainly
   as accepted follow-up work, not as a hidden gap.
