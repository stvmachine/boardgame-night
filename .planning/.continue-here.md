## FEATURES.md — Key findings (from gsd-2)

- **v1 baseline from bggeek-shared-list source**: 16 table-stakes features — multi-user collection merge, fuzzy search (Fuse.js), player count + play time filters, 4 grouping modes (player count, year, rating, "best with"), 6 sort options, hot games landing, permalink URLs, responsive layout
- **Critical limitation to fix**: `useMultiUserCollections` is hardcoded to 2 users ("user1Validation + user2Validation"). Rewrite MUST generalize to N users.
- **Game suggestion algorithm**: Deterministic weighted scoring (0-100) over merged collection — 5 components: player-count suitability via BGG polls (Schmaus adjusted-rating formula, 40% weight), time fit (20%), complexity fit via averageWeight (20%), community rating (10%), optional freshness (10%). Human-readable "why this fits" explanations. NOT ML — transparent, instant, cold-start-safe, tuneable.
- **Auth is the architectural gate**: v1 is anonymous (URL-only permalinks). All night-organizing features (groups, sessions, invitations) require user accounts + BGG username binding.
- **Phase ordering**: Collection parity + auth → Groups + minimal session loop → Suggestion intelligence (poll-based) → Play logging/feedback loop
- **6+ competitors analyzed**: What2Play, DicyNight, Boardy, MeepleUp, GameNight, Game Night Picks — key insight: collection-sharing alone is now table stakes; differentiation lives in sessions + suggestion quality
- **Anti-features**: BGG play write-back (fragile auth), mobile native app (web-first), real-time chat, ML/AI game recommendations (overengineered for v1)

## PITFALLS.md — Key findings (from gsd-4)

- **BGG expansion subtype workaround (CRITICAL)**: BGG API incorrectly labels expansions as `subtype=boardgame` in collection responses. The old proxy solved this with a two-call merge workaround (fetch boardgames, fetch expansions separately, merge). The rewrite MUST replicate this or the core feature silently breaks.
- **BGG HTTP 202 "queued" responses (CRITICAL)**: Old proxy doesn't handle 202 status codes. The rewrite must add retry-on-202 logic (up to 5 retries) before parsing XML, or collections will appear empty.
- **Solid Queue has NO automatic retries (CRITICAL)**: Every BGG job class must declare `retry_on` explicitly. Transient BGG 503 errors will kill jobs silently without it.
- **GraphQL N+1 on BGG expansion resolution**: Old proxy batches expansions in groups of 3 with 10-item limit → 20+ seconds per game. Rewrite must use `GraphQL::Batch` (Shopify gem) with `BGGThingLoader` that batches all expansion IDs into a single BGG `/thing?id=` call.
- **Old app has hardcoded 2-user limit**: Known limitation to fix, not replicate. Design for N users from the start.
- **dry-validation integration friction**: strong_params conflicts, form object patterns, contract design, type coercion surprises
- **Vue 3 + Rails monorepo pitfalls**: build pipeline conflicts (vite_rails vs separate Vite), dev server proxying (CORS, Vite dev → Rails API), deployment complexity
- **Rewrite pitfalls**: over-engineering based on old app, scope creep from "while we're at it", premature optimization
- **BGG rate limiting**: 1 req/5s enforced. Token bucket in Redis recommended. Cache aggressively (Rails cache + stale-while-revalidate).
- **Game suggestion cold start**: Rule-based filtering first, not ML. Use BGG poll data, not the old app's arbitrary heuristic from min/max player range.
- **Phase mapping**: BGG pitfalls → Phase 2 (BGG integration), Solid Queue → Phase 4 (background jobs), GraphQL N+1 → Phase 5 (GraphQL schema), Multi-user → Phase 6 (collections), Suggestions → separate milestone
