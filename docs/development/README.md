# Engineering Blog Maintainer Runbook

The engineering blog lives in `docs/development/`. It is a static site generated by the custom pure-Ruby engine in `lib/dev_blog/` and served from the same Rails/Kamal image as the application and the React SPA.

## What goes here

This directory contains **dated engineering posts** about how the app is built. Each post is a standalone Markdown file with YAML frontmatter. The generator turns every post into a static HTML page under `public/dev-blog/` and produces an index at `/blog/` (and, optionally, at the root of a dedicated subdomain).

Architecture Decision Records (ADRs) are **not** authored here. They stay in `docs/adr/` and are imported from the canonical `docs/adr/README.md` catalog. Do not copy ADR bodies into this directory; the generator reads them in place.

## Post filename and frontmatter rules

Filename pattern:

```text
YYYY-MM-DD-slug.md
```

- `YYYY-MM-DD` must be a real calendar date.
- `slug` must match `[a-z0-9]+(?:-[a-z0-9]+)*` — lowercase letters, digits, and hyphens only. No underscores, spaces, or consecutive hyphens.
- Example: `2026-08-02-graphql-wiring-react-to-rails.md`.

Required frontmatter keys:

```yaml
---
title: "A human-readable title"
date: 2026-08-02
description: "One-line summary for the index page."
tags: [rails, graphql, architecture]
---
```

- `title` — non-empty string.
- `date` — must match the filename date.
- `description` — string, shown in the index.
- `tags` — array of strings; optional but recommended. Empty arrays are fine.

Optional key:

- `draft: true` — excludes the post from the default build. Include drafts with `bin/build-dev-blog --include-drafts`.

Ordering is determined by `date` descending, then `slug` ascending. ADRs are ordered by ADR number.

## Content safety rules

The engine is intentionally small and strict. Do not rely on arbitrary HTML, JavaScript, or exotic URL schemes.

- Write prose and fenced code blocks in Markdown. Do not put `<script>` tags, `onclick=` handlers, or inline `<style>` blocks in the body.
- The converter strips unsafe URI schemes (`javascript:`, `data:`, `vbscript:`, `file:`) and disallows tags like `<script>`, `<style>`, `<iframe>`, `<form>`, `<input>`, and `<button>`.
- Links may be relative (`/some-path`) or absolute `https://` / `mailto:`.
- Never put real credentials, API tokens, private keys, or registry passwords in a post. The CI pipeline and the `content_pipeline_spec` will fail if sentinel secret names or values appear in generated output.

## Building the blog locally

The canonical CLI is `bin/build-dev-blog`. It runs without booting Rails and needs no BGG or dotenv secrets.

```bash
bin/build-dev-blog
```

Defaults:

- `--source` → `docs/development`
- `--output` → `public/dev-blog`
- `--adr-catalog` → `docs/adr/README.md`
- drafts are excluded

Options:

```bash
bin/build-dev-blog --source docs/development \
                   --output public/dev-blog \
                   --include-drafts

bin/build-dev-blog --no-adrs          # skip ADR pages
bin/build-dev-blog --adr-catalog path/to/README.md
```

A Rake wrapper is also available:

```bash
bin/rake dev_blog:build
```

This does not load the Rails environment.

## Generated output layout

`public/dev-blog/` is the default output directory. It is ignored by Git and must not be committed.

```text
public/dev-blog/
├── index.html
├── styles.css
├── posts/
│   └── <slug>/
│       └── index.html
└── adrs/
    └── <NNN-slug>/
        └── index.html
```

- `index.html` — the engineering-journal index, including both posts and accepted ADRs.
- `styles.css` — the shared stylesheet.
- `posts/<slug>/index.html` — one post page.
- `adrs/<NNN-slug>/index.html` — one accepted ADR page (e.g., `adrs/001-monorepo-rails-api-vue-spa/`).

The builder replaces the output directory atomically through a staged swap, so stale files from a previous build are removed and the result is deterministic for the same source.

## Previewing locally

After building:

```bash
bin/build-dev-blog
bin/rails server
```

Visit the primary app blog mount:

```text
http://localhost:3000/blog/
```

`/blog` redirects to `/blog/` so relative asset links resolve correctly.

To test the dedicated-host mount, set `DEV_BLOG_HOST` to a local hostname (for example, add `blog.localhost` to `/etc/hosts` pointing at `127.0.0.1`) and restart the server:

```bash
DEV_BLOG_HOST=blog.localhost bin/rails server
```

Then visit:

```text
http://blog.localhost:3000/
```

## Focused test commands

Run the blog-specific RSpec suites:

```bash
DEV_BLOG_HOST=blog.example.test \
BGG_TOKEN=phase12-secret-sentinel \
DOTENV_PRIVATE_KEY_BGGEEK=phase12-key-sentinel \
rtk rspec spec/lib/dev_blog spec/requests/dev_blog_controller_spec.rb
```

CI runs the same focused suites in `.github/workflows/ci.yml` after building the blog and checking that the expected files exist.

The full Docker image-build example is tagged `:docker` and is intended for CI or a long-running local run. Add `--tag='~docker'` to skip it when running the focused suites locally.

## Accepted ADRs: the canonical lane

- `docs/adr/README.md` is the single catalog of ADRs. Only rows with status `accepted` are published.
- The generator validates every catalog row, the ADR filename, the H1 heading, and the `## Status` section. A malformed or inconsistent catalog raises an error.
- Published ADR pages always include a historical notice: they capture the reasoning at a point in time, and older frontend references (such as Vue) describe historical context, not the current system.
- Do not copy or move ADR files into `docs/development/`. If an ADR needs a correction, update it in `docs/adr/` and, if necessary, reconcile only the title cell in `docs/adr/README.md`.

## Docker image build

The Dockerfile runs `bin/build-dev-blog` in the final Ruby image stage. This needs no `RAILS_MASTER_KEY`, no `BGG_TOKEN`, and no `DOTENV_PRIVATE_KEY_BGGEEK` at build time. After the build stage, the image contains:

- `public/dev-blog/index.html`
- `public/dev-blog/styles.css`
- all `public/dev-blog/posts/*/index.html` files
- all `public/dev-blog/adrs/*/index.html` files matching the accepted ADR catalog count

The full image build is slow locally and is normally verified in CI or with a dedicated long-running local run.

## Kamal deployment and host configuration

The deployment uses two exact hostnames supplied through environment variables:

- `APP_HOST` — the primary application hostname (e.g., `app.example.com`).
- `DEV_BLOG_HOST` — the dedicated blog hostname (e.g., `blog.example.com`).

No invented production value is hardcoded in the repository. The `config/deploy.yml` reads both variables and only emits a `proxy:` block with both hosts when they are configured.

Render the Kamal configuration for verification:

```bash
APP_HOST=app.example.test \
DEV_BLOG_HOST=blog.example.test \
KAMAL_REGISTRY_PASSWORD=phase12-registry-sentinel \
bin/kamal config
```

Deploy normally after the config renders correctly:

```bash
APP_HOST=app.example.com \
DEV_BLOG_HOST=blog.example.com \
KAMAL_REGISTRY_PASSWORD=your-real-registry-token \
bin/kamal deploy
```

The blog host constraint (`DevBlogHostConstraint`) reads `ENV["DEV_BLOG_HOST"]` at runtime and only activates the dedicated-host routes when the value is a valid hostname.

## DNS and TLS

Before either public hostname works:

1. Create A and/or AAAA records for `APP_HOST` and `DEV_BLOG_HOST` pointing to the VPS IP used by Kamal.
2. Ensure ports 80 and 443 are open inbound to the server so Kamal Proxy can answer the Let's Encrypt HTTP-01 challenge and serve HTTPS traffic.
3. Wait for Kamal Proxy to issue a certificate for both hostnames.

Do not start the public checks until DNS and TLS are valid.

## Public URL shapes

Primary application host:

- `https://$APP_HOST/blog/` — index
- `https://$APP_HOST/blog/posts/<slug>/` — post
- `https://$APP_HOST/blog/adrs/<NNN-slug>/` — ADR
- `https://$APP_HOST/blog/styles.css` — stylesheet

Dedicated blog host:

- `https://$DEV_BLOG_HOST/` — index
- `https://$DEV_BLOG_HOST/posts/<slug>/` — post
- `https://$DEV_BLOG_HOST/adrs/<NNN-slug>/` — ADR
- `https://$DEV_BLOG_HOST/styles.css` — stylesheet

Relative links in generated pages are written for the host-root form, so `/blog/` is served by the primary host and `DEV_BLOG_HOST` is served by the dedicated host.

## Rollback

If the blog host deployment fails:

1. Revert the DNS records or point the blog hostname away from the Kamal VPS.
2. Redeploy the previous known-good image:
   ```bash
   APP_HOST=app.example.com \
   DEV_BLOG_HOST=blog.example.com \
   KAMAL_REGISTRY_PASSWORD=your-real-registry-token \
   bin/kamal deploy --version <previous-image-version>
   ```
3. Unset `DEV_BLOG_HOST` if you want to disable the dedicated host entirely; the primary `/blog/` mount remains available as long as the application is deployed.

## What is not in scope

The blog engine is intentionally minimal. The following are deferred unless a future plan explicitly adds them:

- RSS/Atom feeds
- Tag archive pages or search
- Comments, reactions, or analytics
- Pagination
- A CMS or admin authoring interface
- Optional syntax highlighting
- A second runtime service or frontend framework

Keep posts in this directory, ADRs in `docs/adr/`, and generated output in `public/dev-blog/` (ignored).
